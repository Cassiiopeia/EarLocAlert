# 05. 플랫폼 제약

이 앱이 하려는 일 — **앱이 화면에 없어도 위치를 감시하고, 이어폰으로만 소리를 낸다** — 은 OS 가 가장 강하게 제한하는 영역이다.

원 명세([이슈 #1](https://github.com/Cassiiopeia/EarLocAlert/issues/1))는 Android 와 iOS 를 같은 능력으로 가정했다. **그 가정은 틀렸다.** 이 문서는 각 플랫폼이 실제로 무엇을 허용하는지 정리한다.

## 능력 비교

| 항목 | Android | iOS |
|---|---|---|
| 백그라운드 위치 갱신 주기 | 포그라운드 서비스로 **초 단위 가능** | 앱이 지정할 수 없다 |
| 감시 방식 | 직접 폴링 + 자체 판정 | **OS 지오펜스에 위임** |
| 감시 지점 개수 | 실질적 제한 없음 | **앱당 20개** (OS 제한) |
| 진입 감지 지연 | 수 초 | 수십 초 ~ 수 분 (OS 재량) |
| 앱 종료 후 | 서비스가 살아 있음 | **이벤트 발생 시 OS 가 앱을 깨움** |
| 전체화면 알림 | 조건부 가능 | 불가 |
| 상시 표시 알림 | **필수** (포그라운드 서비스) | 없음 |

**같은 앱이지만 동작 방식이 근본적으로 다르다.** 공통 인터페이스 뒤에 두 구현을 둔다 ([02-ARCHITECTURE](02-ARCHITECTURE.md) `features/geofence/data/`).

## Android

### 백그라운드 감시 — MVP 는 OS 지오펜스 위임 ([10-DECISIONS](10-DECISIONS.md) 017)

**MVP 는 Android 도 OS 지오펜스(GeofencingClient)에 위임한다** — native_geofence 가 등록·재부팅 재등록·terminated 발화를 처리한다. 포그라운드 서비스가 없으므로 상시 알림도 없다. F4.5 신뢰 표시는 앱 내 상태 표시로 대체한다.

아래 포그라운드 서비스 명세는 **정밀 모드(재검토 조건: S-2 실측 지연 초과)** 를 위해 남긴다.

### (정밀 모드 예비) 포그라운드 서비스

위치 타입 포그라운드 서비스를 띄우고, 그 안에서 위치를 직접 받아 [03-DOMAIN](03-DOMAIN.md) 의 판정 규칙을 돌린다.

**사용자에게 상시 알림이 보인다.** 이건 없앨 수 없다 — 없애는 방법이 있다면 그건 정책 위반이다. 그러니 이 알림을 **기능으로 쓴다.** "○○ 외 2곳 감시 중" 처럼 지금 무엇을 감시하는지 보여주면, F4.5 가 요구하는 신뢰 표시가 여기서 해결된다.

### 필요한 권한

| 권한 | 시점 | 비고 |
|---|---|---|
| `ACCESS_FINE_LOCATION` | 런타임 | |
| `ACCESS_BACKGROUND_LOCATION` | 런타임, **별도 요청** | API 29+ |
| `POST_NOTIFICATIONS` | 런타임 | API 33+ |
| `FOREGROUND_SERVICE` | 설치 시 | |
| `FOREGROUND_SERVICE_LOCATION` | 설치 시 | API 34+ 필수 |
| `RECEIVE_BOOT_COMPLETED` | 설치 시 | 재부팅 복구 (A-10) |
| `USE_FULL_SCREEN_INTENT` | 설치 시 + **API 34+ 설정 화면** | 아래 참조 |
| `SYSTEM_ALERT_WINDOW` | **설정 화면** | 신뢰성 권한, 아래 참조 (#74) |
| `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` | 런타임 다이얼로그 | 신뢰성 권한, 아래 참조 (#74) |
| `AD_ID` | 설치 시 | 광고 → [09-RELEASE](09-RELEASE.md) |

### 신뢰성 권한 — 필수는 아니지만 없으면 알림이 끊긴다 (#74)

아래 셋은 **거부돼도 앱이 성립해야 하지만**, 없으면 실사용에서 알림이 약해진다. 온보딩의 필수 3종이 끝난 뒤 **한 단계에서 묶어 한 번만** 권하고, 거절하면 다시 묻지 않는다.

| 권한 | 없으면 생기는 일 | 어떻게 받나 |
|---|---|---|
| `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` | Doze·제조사 절전이 지오펜스 콜백을 묶어 늦게 전달한다. 내릴 정류장을 지나서 울린다 | 시스템 다이얼로그 |
| `SYSTEM_ALERT_WINDOW` | 화면이 켜져 있을 때(영상 시청 중) 알림 화면이 뜨지 않고 헤드업 알림으로만 지나간다. 백그라운드 액티비티 시작도 막힌다 | 설정 화면 |
| `USE_FULL_SCREEN_INTENT` (API 34+) | 화면이 꺼졌거나 잠겼을 때 화면을 깨우지 못한다 | 설정 화면 |

판정은 `PermissionSnapshot.canAlertReliably` 하나로 모인다. **`isComplete` 에는 들어가지 않는다** — 이 셋이 없어도 고중요도 알림 + 반복 진동으로 앱은 동작한다.

### 권한 요청 순서를 지켜야 한다

**API 30+ 에서는 백그라운드 위치를 앱 내 다이얼로그로 받을 수 없다.** 시스템 설정 화면으로 보내야 하고, 그마저도 포그라운드 위치를 먼저 허용받은 뒤에만 의미가 있다.

```
1. 위치 권한 필요성 설명 화면        (앱이 직접 그린다)
2. ACCESS_FINE_LOCATION 요청        (시스템 다이얼로그)
3. 허용되면 → 백그라운드 필요성 설명   (앱이 직접 그린다)
4. 설정 화면으로 이동 → "항상 허용"    (시스템 설정)
5. POST_NOTIFICATIONS 요청
```

3번 화면을 건너뛰고 바로 설정으로 보내면 사용자는 무엇을 왜 눌러야 하는지 모른다. **이 흐름이 곧 심사 대응 자료이기도 하다** → [09-RELEASE](09-RELEASE.md)

### 화면을 덮는 수단은 상황별로 다르다 (#74 에서 갱신)

Android 14+ 부터 `USE_FULL_SCREEN_INTENT` 의 자동 부여가 알람·통화 계열 앱으로 제한된다. 자동으로는 받을 수 없으므로 **설정 화면으로 유도해 받는다.**

그리고 받아도 충분하지 않다. **전체화면 알림은 화면이 잠겨 있거나 꺼져 있을 때만 액티비티를 띄운다.** 사용자가 화면을 켜고 다른 앱을 쓰는 중이면 OS 가 헤드업 알림으로 강등하는 것이 정의된 동작이다 — 이것이 "유튜브 보는데 진동만 조금 울리고 끝났다"의 원인이었다.

상황별로 담당이 갈린다:

| 상황 | 수단 | 필요 권한 |
|---|---|---|
| 화면 꺼짐·잠금 | 전체화면 알림 + `showWhenLocked`·`turnScreenOn` | `USE_FULL_SCREEN_INTENT` |
| 화면 켜짐, 다른 앱 사용 중 | 감시 서비스가 앱을 전면으로 띄운다 | `SYSTEM_ALERT_WINDOW` |
| 둘 다 거부됨 | 고중요도 알림 + 반복 진동 (**이것만으로 성립해야 한다**) | 없음 |

세 번째 줄은 여전히 유효하다. 위 둘은 **얹는 것이지 전제가 아니다.**

### 제조사 배터리 최적화가 서비스를 죽인다

표준 Doze 모드는 포그라운드 서비스를 죽이지 않는다. **문제는 제조사 커스텀이다.** 삼성·샤오미·화웨이·오포 등은 자체 절전 정책으로 백그라운드 앱을 종료시킨다.

이건 코드로 해결할 수 없다. **사용자에게 배터리 최적화 제외를 안내해야 한다.**

- 최초 설정 시 안내 화면 1회
- 설정 화면에 상시 진입점
- 감시가 비정상 종료된 흔적이 있으면 다시 안내

이게 이 앱의 Android 쪽 최대 신뢰성 리스크다. **"안 울렸다"는 리뷰의 대부분이 여기서 나온다.**

**#74 에서 구현했다** — 온보딩의 신뢰성 권한 단계가 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 를 요청하고, `AlertWatchService` 가 감시 대상이 있는 동안 위치 타입 포그라운드 서비스를 유지한다. 예외를 받지 못한 기기에서는 여전히 지연될 수 있고, 그 경우 남는 것은 알림과 반복 진동이다.

### 재부팅 복구

부팅 완료 브로드캐스트를 받아 서비스를 다시 띄우고, 저장된 지오펜스 상태를 복원한다 ([03-DOMAIN](03-DOMAIN.md) 저장소 경계).

상태를 메모리에만 뒀다면 재부팅 후 전부 `unknown` 이 되어 **첫 진입 알림을 놓친다.**

## iOS

### 백그라운드 감시 — OS 에 위임

앱이 직접 폴링하지 않는다. **OS 지오펜스에 등록하고 이벤트를 기다린다.**

앱이 완전히 종료된 상태에서도 OS 가 이벤트 발생 시 앱을 백그라운드로 깨운다. 이때 UI 는 없다 ([02-ARCHITECTURE](02-ARCHITECTURE.md) 규칙 5).

### 감시 지점 20개 제한

**OS 제한이며 우회 방법이 없다.** 앱당 20개다.

MVP 는 사용자 등록 상한을 이 이하로 둔다. 상한에 도달하면 새 등록을 막고 이유를 화면에 표시한다 ([01-REQUIREMENTS](01-REQUIREMENTS.md) F1).

> 등록 위치가 20개를 넘는 사용자가 생기면, **현재 위치에서 가까운 순으로 20개만 OS 에 등록하고 이동에 따라 교체**하는 방식이 필요하다. Phase 2 이후 판단 → [11-ROADMAP](11-ROADMAP.md)

### 반경 하한

**아주 작은 반경은 신뢰할 수 없다.** OS 가 등록은 받아주지만 실제 발화가 부정확하다.

F1.4 는 50m 부터 허용하는데, iOS 에서 50m 가 실용적인지는 **실측으로 확인해야 한다.** 부정확하면 iOS 하한을 따로 두고 화면에 안내한다 → [11-ROADMAP](11-ROADMAP.md)

### 권한 — "항상 허용"을 처음부터 요구하지 않는다

iOS 는 앱이 곧바로 "항상 허용"을 요청하면 사용자가 거부할 확률이 높다. **사용 중 허용을 먼저 받고**, 앱이 백그라운드 감시를 실제로 시작할 때 상향을 요청한다.

```
1. 필요성 설명 화면
2. 사용 중 허용 요청
3. 지오펜스 등록 → OS 가 적절한 시점에 "항상 허용" 여부를 사용자에게 묻는다
4. 알림 권한 요청
```

`Info.plist` 의 용도 설명 문구는 **심사 대상이다.** "위치가 필요합니다" 같은 문구는 반려된다. 무엇을 위해 언제 쓰는지 구체적으로 쓴다 → [09-RELEASE](09-RELEASE.md)

### 전체화면 알림은 없다

iOS 에 전체화면 알림 개념이 없다. 잠금화면·배너 알림이 전부다.

소리를 무음 모드에서도 강제로 내는 Critical Alert 는 **Apple 의 별도 승인이 필요하며, 이 앱의 용도로는 승인되지 않는다고 보는 것이 안전하다.** 신청하지 않는다.

### 반복 진동의 제약

iOS 는 앱이 백그라운드에서 임의로 반복 진동을 발생시키기 어렵다. F3.1(반복 진동)을 iOS 에서 어떻게 달성할지는 **미검증 항목이다.**

현실적인 수단은 **짧은 간격으로 알림을 여러 개 예약**하는 것이고, 사용자가 해제하면 남은 예약을 취소한다. 이 방식이 실제로 원하는 체감을 주는지 실기기 확인이 필요하다 → [11-ROADMAP](11-ROADMAP.md)

## 오디오 라우팅 — F3.4 / F3.5 / F3.7

### 핵심 사실: "이어폰으로만 보내기"는 특별한 기술이 아니다

두 OS 모두 **이어폰이 연결되어 있으면 미디어 재생이 자동으로 그리로 간다.** 앱이 억지로 라우팅을 조작할 필요가 없다.

그래서 이 앱이 해야 할 일은 반대다.

> **본인만 듣는 출력이 없으면 재생하지 않는다.**

스피커로 새는 사고는 "라우팅에 실패해서" 생기는 게 아니라 **"연결 여부를 확인하지 않고 재생해서"** 생긴다. 판정 로직은 [03-DOMAIN](03-DOMAIN.md) 규칙 5에 있다.

### 확인해야 할 것

`audio_session` 의 `getDevices(includeInputs: false)` 로 출력 장치 목록을 받아 **허용 목록에 있는 종류가 하나라도 있는지** 본다. 양 OS 가 같은 코드다.

| 포함 (`AudioDeviceType`) | 제외 |
|---|---|
| `wiredHeadset` · `wiredHeadphones` | `builtInSpeaker` · `builtInSpeakerSafe` · `builtInEarpiece` |
| `usbAudio` | `carAudio` · `airPlay` |
| `bluetoothA2dp` · `bluetoothSco` · `bluetoothLe` | `hdmi` · `hdmiArc` · `dock` |
| `hearingAid` | `lineAnalog` · `lineDigital` · `auxLine` · `unknown` |

**허용 목록이다 — 모르는 장치는 자동으로 제외된다.** 유선 이어폰을 블루투스와 동일하게 취급하기로 결정했다 → [10-DECISIONS](10-DECISIONS.md) 018

재생은 해제할 때까지 반복한다. **`play()` 의 Future 를 기다리면 안 된다** — 반복 재생은 끝나지 않아 호출자가 영원히 막힌다.

### 실패 시 동작

오디오 세션 설정이 실패하거나 재생이 실패하면 **소리를 포기하고 진동으로 떨어진다.** 재시도하지 않는다.

재시도 중에 라우팅이 바뀌어 스피커로 나가는 것이 최악의 시나리오다. F3.7 은 소리를 내는 것보다 우선한다.

### 무음 모드와의 관계

기기가 무음 모드일 때 이어폰으로 소리를 낼지는 **미검증 항목**이다. iOS 는 오디오 세션 카테고리에 따라 동작이 달라진다.

원칙: **무음 모드를 무시하고 강제로 소리를 내지 않는다.** 사용자가 무음으로 둔 데는 이유가 있고, 이 앱은 애초에 "조용함"이 가치다.
