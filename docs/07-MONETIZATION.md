# 07. 수익화

## 전제 — 이 앱은 광고를 띄우기 어려운 구조다

먼저 인정하고 시작해야 하는 사실이다.

일반적인 앱은 사용자가 앱을 열어 여러 화면을 오가고, 그 사이사이에 광고를 넣는다. **이 앱은 그 전제가 성립하지 않는다.** 위치를 등록하면 그 뒤로 앱이 열리지 않는다.

| 지면 후보 | 노출 빈도 | 평가 |
|---|---|---|
| **알림 해제 후 화면** | **알림이 울릴 때마다** | 사실상 유일한 정기 노출 |
| 위치 목록 · 설정 배너 | 가끔 | 부수적 |
| 위치 추가 화면 | 초기 1~2회 | 무시할 수준 |
| 앱 시작 시 | 거의 없음 | 게다가 정책 위반 소지 |

**그래서 알림 해제 흐름이 곧 수익 구조다.** 이건 나중에 붙이는 기능이 아니라 [06-UX](06-UX.md) 의 핵심 화면 설계에 처음부터 포함된다.

역설적이지만 이 구조에는 장점이 하나 있다. **알림이 자주 울린다 = 앱을 잘 쓰고 있다 = 광고가 많이 노출된다.** 사용자 가치와 수익이 같은 방향을 본다. 사용자를 억지로 앱에 붙잡아둘 이유가 없다.

## 지면 설계

### 1. 전면광고 — 알림 해제 후

```
알림 화면
  └─ [알림 끄기] 탭
      ├─ 즉시: 진동·소리 중단              ← 광고와 무관하게 항상 실행
      └─ 해제 완료 화면
          └─ 전면광고 (조건 충족 시)
```

**해제와 광고 사이에 어떤 의존도 없다.** 광고가 로딩되지 않았으면 그냥 넘어간다. 기다리지 않는다 ([02-ARCHITECTURE](02-ARCHITECTURE.md) 규칙 4).

미리 로딩해 둔다 — 알림이 발화하는 시점에 광고를 요청해 두면, 사용자가 해제할 때쯤 준비가 끝나 있다. 다만 **미리 로딩에 실패해도 아무 일도 일어나지 않아야 한다.**

### 2. 배너 — 위치 목록 · 설정 화면 하단

고정 배너. 화면 콘텐츠를 가리지 않는다.

**지도 화면에는 배너를 넣지 않는다.** 지도는 위치를 찍는 화면이고, 하단에 배너가 있으면 그 영역을 탭하다 광고를 누르게 된다. 우발적 클릭은 계정 정지 사유다.

## 빈도 제어

전면광고를 무제한으로 띄우면 **정책 위반이자 앱 삭제 사유**다. 알림이 5분 간격으로 두 번 울렸는데 광고가 두 번 뜨면 사용자는 그걸 참지 않는다.

| 규칙 | 값 | 근거 |
|---|---|---|
| 최소 노출 간격 | **3분** | 연속 알림 시 중복 노출 차단 (F8.3) |
| 1일 노출 상한 | 설정값으로 관리 | 과다 노출 방지 (F8.4) |
| 앱 최초 실행 | 노출 안 함 | 첫인상을 광고로 만들지 않는다 |
| 동의 거부 상태 | 비개인 맞춤 광고로 전환 | UMP 결과에 따름 |

노출 시각과 횟수는 `SharedPreferences` 에 저장한다 ([03-DOMAIN](03-DOMAIN.md) 저장소 경계). 앱을 껐다 켜도 유지되어야 한다.

**빈도 제어는 반드시 단위 테스트로 검증한다** ([04-CONVENTIONS](04-CONVENTIONS.md)). 이 로직이 조용히 깨지면 계정이 정지되고, 정지되면 되돌릴 방법이 마땅치 않다.

## 정책 경계 — 하면 안 되는 것

## 실제 광고는 언제 나가는가 (이슈 #109)

**배포 빌드임이 확인됐을 때만 나간다.** 나머지는 전부 테스트 광고다.

| 상황 | 광고 |
|---|---|
| 디버그 빌드 | 테스트 |
| 검증 빌드 (`.env` 의 `DEV_FLAG=true`) | 테스트 |
| **빌드 성격을 읽지 못함** | **테스트** |
| 배포 빌드 (`DEV_FLAG` 없음) | 실제 |

세 번째 줄이 핵심이다. `DevFlag` 는 `true`/`false`/`못 읽음` 세 상태를 갖는데, 이분법으로 두면 못 읽은 경우가 어느 한쪽에 붙어 반드시 위험해진다 — 실제 광고 쪽에 붙으면 검증 중 무효 트래픽이 되고, 그것이 누적되면 계정 정지다.

**광고가 안 나가는 것은 수익 손실이지만, 잘못 나가는 것은 되돌릴 수 없다.**

발급된 ID (공개 정보라 소스에 둔다 — APK 를 뜯으면 그대로 나온다):

| 항목 | 위치 |
|---|---|
| 앱 ID | `AndroidManifest.xml` 메타데이터. **없으면 앱이 시작 시 크래시**하므로 `.env` 로 빼지 않는다 |
| 전면 단위 ID | `AdUnitIds._prodInterstitialAndroid` |
| iOS | 미등록 (#51 로 서명이 막혀 있다). 비어 있으면 테스트 ID 로 떨어진다 |

**예전에는 `--dart-define` 으로 받았는데 CI 가 그것을 넘기지 않아 릴리스 빌드도 테스트 광고로 나가고 있었다.** 그 워크플로우는 템플릿이 관리해서 고쳐도 다음 갱신에 덮인다.

---

AdMob 정책 위반은 경고가 아니라 **계정 정지**로 온다. 정지되면 그 계정으로 만든 다른 앱의 수익도 함께 끊긴다.

| 금지 | 왜 위험한가 |
|---|---|
| 알림 화면 **위에** 광고 배치 | 급하게 해제하려다 광고를 누른다 = 우발적 클릭 유도 |
| 해제 버튼 근처에 광고 | 같은 이유 |
| 앱 시작 직후 전면광고 | "예기치 않은 시점의 광고" |
| 조작 중간에 끼어드는 전면광고 | 같은 이유 |
| 광고를 닫아야 기능이 동작 | 강제 상호작용 |
| 광고 클릭 유도 문구 | 명백한 위반 |
| 자기 앱 광고 반복 클릭 | 무효 트래픽 — 즉시 적발된다 |
| 실기기 테스트에서 실제 광고 ID 사용 | 무효 트래픽으로 집계된다 |

마지막 항목이 실수하기 가장 쉽다. **개발·테스트 빌드는 테스트 광고 ID 를 쓴다** (F8.6). 강제 방법은 [08-OPERATIONS](08-OPERATIONS.md).

## 광고 ID 관리

| 구분 | 값 | 관리 |
|---|---|---|
| AdMob 앱 ID | 공개 정보 | 매니페스트·plist 에 직접 넣는다 |
| 광고 단위 ID (프로덕션) | 공개 정보지만 오용 방지 필요 | 빌드 설정으로 주입 |
| 광고 단위 ID (테스트) | Google 공개 테스트 ID | 소스에 상수로 둔다 |

**AdMob 앱 ID 는 비밀이 아니다.** APK 를 뜯으면 나온다. 숨기려고 애쓸 필요 없다.

중요한 것은 **빌드 종류에 따라 자동으로 갈리는 것**이다. 사람이 기억해서 바꾸는 방식이면 언젠가 실수한다.

```
디버그 빌드   → 테스트 광고 ID  (항상)
릴리스 빌드   → 프로덕션 광고 ID
```

## 동의 수집 (UMP)

Google User Messaging Platform 으로 광고 개인화 동의를 받는다 (F8.5).

| 항목 | 내용 |
|---|---|
| 시점 | 앱 최초 실행, 권한 온보딩과 별도로 |
| 거부 시 | 비개인 맞춤 광고로 계속 노출 |
| 대상 | 유럽 경제 지역·영국 필수. **글로벌 배포면 한국 타겟이어도 필요하다** |

iOS 는 여기에 **ATT(앱 추적 투명성)** 가 추가된다 → [09-RELEASE](09-RELEASE.md)

**동의 화면을 권한 온보딩과 같은 흐름에 섞지 않는다.** 위치 권한을 설명하는 중간에 광고 동의가 끼면 사용자가 전부 거부한다.

## 스토어 심사와의 관계

**광고는 1차 심사부터 포함해서 제출한다.** → [10-DECISIONS](10-DECISIONS.md)

나중에 광고를 붙이면 다음이 전부 따라온다.

- 앱 업데이트 재심사
- 개인정보 처리방침 개정
- Play 데이터 보안 양식 수정 (광고 ID 수집 신고)
- iOS Privacy Manifest 수정
- ATT 권한 추가 → 심사 항목 추가

이걸 두 번 하는 것보다 처음부터 한 번에 하는 편이 낫다. 상세 체크리스트는 [09-RELEASE](09-RELEASE.md).

## 기대치

**이 앱의 광고 수익은 크지 않을 것으로 본다.** 노출 지면이 구조적으로 하나뿐이고, 사용자 한 명이 하루에 만드는 노출이 많아야 한두 번이다.

수익은 **사용자 수 × 알림 발생 빈도**로 결정된다. 앱 사용 시간을 늘리는 흔한 수법(체류 시간 늘리기, 화면 더 보게 하기)이 이 앱에는 통하지 않는다 — 애초에 앱을 안 여는 것이 이 앱의 가치이기 때문이다.

그러니 **광고를 더 넣어 수익을 늘리려는 시도를 하지 않는다.** 지면을 억지로 늘리면 정책 위반에 가까워지고, 앱의 가치가 훼손되며, 리뷰 별점이 떨어진다. 위 설계가 이 구조에서의 상한이다.

실제 수치는 출시 후 측정한다. 측정 전에 수익을 추정해 계획을 세우지 않는다.

### 다른 수익 모델은 Phase 4 이후에 판단한다

| 후보 | 검토 시점 |
|---|---|
| 광고 제거 인앱결제 | 사용자 기반이 생긴 뒤 |
| 위치 개수 상한 해제 | iOS 20개 제약 때문에 팔 수 있는 것이 제한적이다 |
| 구독 | 이 앱의 기능량으로는 정당화하기 어렵다 |

**MVP 단계에서는 광고만 한다.** 결제를 붙이면 심사 항목과 세금·환불 처리가 따라오고, 출시가 더 밀린다.
