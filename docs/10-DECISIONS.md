# 10. 결정 기록

설계 판단을 여기 모은다. **"왜 이렇게 되어 있지?"** 의 답은 이 문서에 있다.

각 항목은 `결정 / 버린 것 / 근거 / 재검토 조건` 으로 쓴다. **재검토 조건이 중요하다** — 지금 옳은 결정이 영원히 옳지는 않고, 어떤 조건이 바뀌면 다시 볼지 적어두지 않으면 아무도 다시 보지 않는다.

**판단을 바꿨으면 항목을 추가한다.** 기존 항목을 지우지 않고 `대체됨` 으로 표시한다.

---

## 001. feature-first + feature 내 3계층

**버린 것** — 타입별 계층 구조(`models/`·`screens/`·`services/`), 전역 클린 아키텍처 3계층

**근거**

이 앱에서 검증하기 가장 어려운 것은 **지오펜스 판정**과 **오디오 경로 결정**이다. 둘 다 실기기에서만 확인할 수 있게 되면 개발 속도가 무너진다.

`features/<name>/domain/` 에 Flutter 의존 없는 순수 로직을 두면, 실기기 없이 "밖에 있다가 들어왔을 때 알림이 나가는가", "블루투스가 없을 때 소리를 안 내는가"를 테스트로 확인할 수 있다.

타입별 구조를 버린 이유는 `services/` 가 커질수록 경계가 사라지기 때문이다. 다른 Flutter 프로젝트(RomRom-FE)가 그 구조인데, 그건 그 프로젝트의 선택이고 이 앱의 요구와는 다르다.

전역 클린 아키텍처를 버린 이유는 1인 개발 규모에 보일러플레이트가 과하기 때문이다. **경계는 feature 단위로 충분하다.**

**재검토 조건** — feature 가 8개를 넘어가면 feature 간 조율을 `app` 하나가 감당하지 못한다. 그때 조율 계층을 나눈다.

## 002. Riverpod code generation 단독

**버린 것** — `provider` 패키지 병행, 손으로 선언하는 Provider, `get_it`

**근거**

**혼용이 문제다.** 상태 관리 방법이 둘이면 파일마다 규칙이 달라지고, `riverpod_lint` 가 절반만 검사한다. 새 화면을 만들 때마다 "이 화면은 어느 쪽이지"를 확인해야 한다.

DI 도 Riverpod 으로 통일한다. `get_it` 을 함께 쓰면 의존성이 두 곳에 등록되고, 테스트에서 무엇을 갈아끼워야 하는지 알기 어려워진다.

**재검토 조건** — 없다. 이건 되돌리지 않는다. 되돌린다면 전면 교체이지 병행이 아니다.

## 003. 로컬 저장소는 Drift

**버린 것** — Hive, Isar, 도메인 데이터를 SharedPreferences 에 넣는 것

**근거**

저장할 데이터가 많지 않다(위치 20개 남짓). 그래서 SharedPreferences 로도 될 것 같지만, **`GeofenceEvent` 이력이 시간순 조회와 기간 삭제를 요구한다.** 그건 SQL 이 하는 일이다.

Hive 는 원 명세의 후보였으나 현재 유지보수 상태가 불확실하다. **저장소는 앱의 수명 동안 계속 쓰이는 부품이라 유지보수 상태가 기능보다 중요하다.**

**재검토 조건** — Drift 의 코드 생성이 빌드 시간에 부담이 될 정도로 스키마가 커지면. 현재 예상 규모에서는 일어나지 않는다.

## 004. 백그라운드 감시 — 플랫폼별로 다른 전략

**버린 것** — 양 플랫폼 동일 구현, 양쪽 모두 OS 지오펜스 위임, Android 우선 출시

**근거**

원 명세는 "3초 주기 백그라운드 폴링"을 양 플랫폼 공통으로 적었다. **iOS 는 그걸 허용하지 않는다.**

핵심 시나리오가 "셔틀버스에서 졸다가 목적지를 지나치는 것 방지"인데, 이건 **알림 지연이 곧 실패**다. 양쪽 다 OS 지오펜스로 통일하면 Android 에서도 수십 초 지연이 생겨 핵심 가치가 약해진다.

그래서 Android 는 포그라운드 서비스로 정밀 감시하고, iOS 는 OS 에 위임한다. **iOS 가 열등한 게 아니라 OS 가 허용하는 최선이 다른 것이다.** 이 차이는 숨기지 말고 사용자에게 알린다.

Android 우선 출시를 버린 이유는 TestFlight 파이프라인이 이미 완성되어 있어 iOS 를 미룰 실익이 적기 때문이다.

**재검토 조건** — iOS 가 백그라운드 위치 정책을 완화하면. 또는 Android 제조사 절전으로 포그라운드 서비스가 실용성을 잃으면.

## 005. 배터리 목표 수치를 철회한다

**버린 것** — "하루 15% 미만" (원 명세 3.1)

**근거**

**3초 폴링과 15% 는 양립하지 않는다.** 둘 다 문서에 적으면 둘 중 하나가 반드시 거짓말이 된다.

측정하지 않은 수치를 목표로 적으면 나중에 그 수치를 맞추려고 기능을 깎거나, 아니면 그냥 무시하게 된다. 어느 쪽도 좋지 않다.

**실측 후 확정한다.** 그때까지 이 항목은 비워둔다.

**재검토 조건** — 출시 후 1개월 실측 데이터가 모이면 수치를 확정해 [01-REQUIREMENTS](01-REQUIREMENTS.md) 4.1 에 기록한다.

## 006. 전체화면 알림을 전제하지 않는다

**버린 것** — "Full-screen 팝업 알림" 을 필수 요구사항으로 두는 것 (원 명세 F3.2)

**근거**

iOS 에는 전체화면 알림 개념이 없다. Android 도 14 부터 권한 자동 부여가 알람·통화 계열로 제한되어, 이 앱이 받을 수 있는지 확정할 수 없다.

**받을 수 있을지 모르는 것을 필수 요구사항으로 두면 안 된다.** 높은 중요도 알림 + 반복 진동만으로 앱이 성립하도록 설계하고, 전체화면은 되면 얹는다.

**재검토 조건** — Android 에서 실제로 권한이 부여되는 것이 확인되면 우선 수단으로 승격한다.

> **2026-08-06 갱신 (#74)** — 실기기 검증에서 **이 결정의 전제가 틀렸다는 것이 드러났다.** 자동 부여만 없는 것이 아니라, 권한을 받아도 전체화면 알림은 **잠금·화면 꺼짐 상태에서만** 액티비티를 띄운다. 사용 중에는 OS 가 헤드업으로 강등하는 것이 정의된 동작이라, 영상 시청 중에는 어떤 경우에도 화면이 덮이지 않는다.
>
> 결론의 **후반부는 유지한다** — 알림 + 반복 진동만으로 성립해야 한다는 것. **전반부는 뒤집는다** — 전체화면을 "기대하지 않는" 대신 설정 화면으로 유도해 받고, 화면이 켜져 있는 경우는 별도 수단(`SYSTEM_ALERT_WINDOW`)으로 덮는다. 019 를 참조한다.

## 007. "스피커 무음"의 구현 방향

**버린 것** — 오디오 라우팅을 강제로 조작해 이어폰으로 보내는 방식

**근거**

원 명세는 "블루투스 감지 → 이어폰으로 라우팅"을 기술 과제로 적었다. 그런데 **양 OS 모두 블루투스가 연결되어 있으면 미디어가 자동으로 그리로 간다.** 앱이 라우팅을 조작할 필요가 없다.

스피커로 새는 사고는 라우팅 실패가 아니라 **연결 여부를 확인하지 않고 재생해서** 생긴다. 그래서 문제를 뒤집는다.

> 블루투스가 연결되어 있지 않으면 **재생하지 않는다.**

이렇게 하면 판정이 `bool` 하나를 받는 순수 함수가 되고, 실기기 없이 네 가지 경우를 전부 테스트할 수 있다. 라우팅 조작 방식은 테스트가 불가능하다.

오디오 세션 설정이 실패하면 재시도하지 않고 진동으로 떨어진다 — **재시도 중 라우팅이 바뀌어 스피커로 나가는 것이 최악**이다.

**재검토 조건** — 실기기 검증에서 자동 라우팅이 기대와 다르게 동작하면.

## 008. 지도·검색은 Google 로 통일

**버린 것** — 카카오 로컬 API 병행, OSM(flutter_map) + Nominatim

**근거**

명세에 한국어·영어 지원이 있다. 카카오 검색은 한국 POI 정확도가 높지만 해외 검색이 안 된다. 제공자를 둘로 나누면 **국내/해외 분기 코드가 생기고 그만큼 틀릴 여지가 늘어난다.**

OSM 은 무료지만 한국 지도 데이터가 빈약하고, Nominatim 은 상업적 이용과 요청 빈도에 제약이 있다.

모바일 지도 표시는 무료이고 과금은 검색(Places)에서 발생하는데, 검색은 Phase 2 기능이고 개인 앱 규모에서는 무료 크레딧 범위에 들어간다.

**재검토 조건** — 사용자가 늘어 Places 과금이 실제로 발생하면 한국 검색만 카카오로 분리한다. 그때는 사용자 수가 근거가 되므로 분기 비용을 감당할 이유가 생긴다.

## 009. 광고를 1차 심사부터 포함한다

**버린 것** — 먼저 출시하고 나중에 광고를 붙이는 방식

**근거**

나중에 붙이면 **재심사 + 개인정보 문서 전면 수정**이 따라온다.

- 앱 업데이트 심사
- 개인정보 처리방침 개정
- Play 데이터 보안 양식 수정
- iOS Privacy Manifest 수정
- ATT 권한 추가 → 심사 항목 증가

같은 일을 두 번 하게 된다. **광고 SDK 가 들어 있다고 심사가 까다로워지지 않는다** — 광고는 대부분의 무료 앱에 있다.

**재검토 조건** — 없다.

## 010. 광고 지면은 알림 해제 후 전면광고

**버린 것** — 배너만 보수적으로, 리워드 광고 병행, 앱 시작 시 광고

**근거**

이 앱은 **사용자가 앱을 열지 않는다.** 배너를 아무리 잘 배치해도 볼 화면이 안 열린다. 유일하게 정기적으로 열리는 순간이 알림이 울릴 때다.

알림 해제 후 전면광고는 알람 앱들이 쓰는 검증된 패턴이고, **사용자가 액션을 취한 뒤의 자연스러운 전환 지점**이라 정책상 문제가 없다.

리워드 광고를 버린 이유는 무료 기능을 잠그는 설계가 되기 때문이다. 위치 개수 제한은 iOS 의 OS 제약(20개)이라 팔 수 있는 것도 아니다.

**금지 사항이 함께 확정된다** — 알림 화면 위에 광고를 겹치지 않는다. 급하게 해제하려다 광고를 누르면 우발적 클릭 유도로 계정이 정지된다.

**재검토 조건** — 출시 후 실제 노출·수익 데이터가 모이면 지면 추가 여부를 판단한다. **다만 알림 화면에 광고를 넣는 선택지는 영구히 제외한다.**

## 011. `alert` 는 `ads` 를 기다리지 않는다

**버린 것** — 광고를 보여준 뒤 알림을 해제하는 흐름

**근거**

수익 관점에서는 광고를 먼저 보여주는 편이 유리해 보인다. **그렇게 하면 앱이 죽는다.**

버스에서 알림이 울려 급하게 껐는데 광고 로딩 때문에 진동이 몇 초 더 계속되면, 사용자는 그 앱을 지우고 별점 1점을 남긴다. 그리고 그 리뷰는 남는다.

광고 수익의 상한은 사용자 수인데, **알림 신뢰성이 무너지면 사용자 수가 0 으로 간다.** 계산이 성립하지 않는다.

이 규칙은 문서로만 지킬 수 없어서 **테스트로 강제한다** — 광고 로딩이 영원히 끝나지 않는 가짜 구현을 넣고도 해제가 즉시 완료되는지 검증한다.

**재검토 조건** — 없다.

## 012. 백그라운드 위치로 정면돌파한다

**버린 것** — 포그라운드 전용으로 먼저 출시하고 백그라운드는 2차 업데이트

**근거**

포그라운드 전용 앱은 **사용자가 화면을 계속 보고 있어야 동작한다.** 그러면 알림이 필요 없다. 앱의 존재 이유가 사라진다.

그 상태로 출시하면 초기 리뷰가 나빠지고, 나중에 백그라운드를 붙여도 그 리뷰는 남는다. **스토어 실적을 먼저 확보한다는 이점보다 첫인상을 망치는 손해가 크다.**

Play 의 백그라운드 위치 심사가 까다롭지만, 이 앱은 **정당한 사유가 실제로 있다.** 억지 명분이 아니므로 자료를 제대로 준비하면 통과 가능성이 낮지 않다.

**재검토 조건** — 권한 선언이 2회 이상 반려되면 포그라운드 버전 우선 출시를 다시 검토한다.

그래서 [09-RELEASE](09-RELEASE.md) 의 체크리스트를 개발과 **병행해서** 채운다.

**재검토 조건** — 없다.

## 014. 문서 축을 앱 프로젝트에 맞게 잡는다

**버린 것** — 서버 프로젝트(palim)의 문서 축을 그대로 복제하는 것

**근거**

palim 은 서버라 `INTEGRATION`(외부 연동)·`SECURITY`(위협 모델)가 핵심 축이다. 이 앱은 다르다.

반대로 서버의 위협 모델·트랜잭션 규약은 이 앱에 해당 사항이 적다.

**재검토 조건** — 서버를 붙이게 되면(동기화 기능) 보안 문서를 추가한다.

## 015. 디자인 — Material 3 기반 + 자체 토큰 레이어

**버린 것** — 서드파티 UI 킷 전면 도입(forui·shadcn_ui 계열), 전면 커스텀 위젯 시스템

**근거**

"깔끔한 앱"은 예쁜 컴포넌트에서 나오지 않는다. **규칙이 적어서** 나온다. 색이 8개고 간격이 4개면 무엇을 조합해도 통일감이 유지된다.

그래서 레이어마다 판단이 다르다.

| 레이어 | 방식 | 이유 |
|---|---|---|
| 기본 위젯 (버튼·시트·다이얼로그) | **Material 3 그대로** | 이미 있고 접근성·플랫폼 대응이 되어 있다 |
| 아이콘 | **Material `_outlined`** | 의존성 0. 변형만 통일하면 톤이 맞는다 |
| 색·타이포·간격·형태 | **자체 토큰** | **여기가 미감을 결정한다** |
| 앱 고유 화면 (알림 화면) | 자체 | 라이브러리가 대신 못 한다 |

서드파티 UI 킷을 버린 이유는 품질이 아니라 **결이 다르기 때문**이다. shadcn 계열은 Tailwind·Radix 기반의 서구권 웹 미감(얇은 보더, 조밀한 여백, 작은 타이포)이라 데스크톱 대시보드에 맞는다. 이 앱이 지향하는 것은 큰 한글 타이포와 넉넉한 여백이다.

전면 커스텀도 버린다. 버튼·시트·리플을 직접 만들 이유가 없다.

**재검토 조건** — 화면이 15개를 넘어가거나 디자이너가 합류하면 컴포넌트 킷 도입을 다시 본다. 그 전에는 토큰만으로 충분하다.

상세는 [06-UX](06-UX.md).

## 016. 알림 해제는 탭 버튼 — 스와이프를 쓰지 않는다

**버린 것** — 스와이프 해제 (참조한 핀테크 UI 의 패턴)

**근거**

핀테크 앱이 송금 확정에 스와이프를 쓰는 것은 **되돌릴 수 없는 동작을 신중하게** 만들기 위해서다. 목적이 "실수 방지"다.

알림 해제는 정반대다. 버스에서 졸다 깨어 **몇 초 안에** 꺼야 하고, 한 손이며, 눈이 반쯤 감겨 있다. 여기서 스와이프를 요구하면 실패한다.

미감은 가져오되 상호작용은 가져오지 않는다. **화면 하단 절반을 차지하는 탭 버튼**으로 간다.

**재검토 조건** — 오탭으로 알림이 꺼진다는 사용자 피드백이 실제로 들어오면. 그때도 스와이프가 아니라 버튼 위치 조정을 먼저 본다.

## 017. 백그라운드 감시 패키지 — native_geofence, MVP 는 양 플랫폼 OS 위임 (004 수정)

**버린 것** — Android 포그라운드 서비스 정밀 감시(004의 원안), flutter_background_geolocation(유료), geofence_service(deprecated), geofencing_api(무활동·앱 생존 시에만), flutter_foreground_task + geolocator 조합(iOS 15분 제약 + Android 만을 위한 별도 코드 경로)

**근거**

S-1 조사(2026-08-04, pub.dev·GitHub 실측)에서 **native_geofence** 가 요구사항 정합성이 가장 높았다:

- 양 플랫폼 모두 OS 네이티브 지오펜스 API (Android GeofencingClient / iOS region monitoring)
- **앱 종료(terminated) 상태 발화 + 재부팅 자동 재등록** — A-10 을 패키지가 해결한다
- MIT 무료. 광고 수익 기반 무료 앱에 유료 라이선스($399+)는 성립하지 않는다
- 활발한 유지보수 (2026-06 기준)

004 는 Android 를 포그라운드 서비스로 정밀 감시하기로 했다. 그러나 FGS 는 **제조사 절전에 죽고, 죽으면 감시가 통째로 사라진다** — 이 앱의 최대 리스크(11-ROADMAP)다. OS 지오펜스는 앱 생존과 무관하게 OS 가 발화를 보장한다. MVP 에서는 "정밀하지만 죽을 수 있는 감시"보다 **"수십 초 늦어도 반드시 울리는 감시"** 가 낫다고 판단했다. 감지 지연은 등록 시 `notificationResponsiveness` 기본값(최대 응답성)으로 최소화한다.

구현은 `GeofenceMonitor` 인터페이스 뒤에 있다 — Android 정밀 모드(FGS + 위치 스트림 + 기존 PositionSample 판정)를 추가해도 화면·도메인은 바뀌지 않는다.

**재검토 조건** — 실기기 스파이크 S-2·S-3 실측에서 진입 감지 지연이 핵심 시나리오(셔틀버스 하차)를 깨뜨리면 Android 정밀 모드를 추가한다. iOS 재부팅 후 중복 발화(패키지 알려진 이슈)는 도메인 규칙 4(같은 상태 반복 무알림)가 걸러낸다 — 실기기에서 확인한다.

> **재검토 결과 (2026-08-14, [이슈 #93](https://github.com/Cassiiopeia/EarLocAlert/issues/93))** — 조건이 발동했고, 지연이 아니라 **발화 자체가 없어** 조건을 초과했다. 원인은 감지 지연이 아니라 이 패키지의 Android 이벤트 전달이 WorkManager 에 갇히는 것이었다. **Android 는 [024](#024-android-는-하이브리드-감시로-전환한다-017-재검토-조건-발동) 로 대체했다.** iOS 는 이 결함이 없어 그대로 유지한다.

## 018. 유선 이어폰도 블루투스와 동일하게 취급한다 (007 확장)

**버린 것** — 블루투스 출력만 "안전한 출력"으로 보는 방식

**근거**

007 은 "블루투스가 연결되어 있지 않으면 재생하지 않는다"로 규칙을 세웠고, 구현도 `isBluetoothConnected` 라는 이름으로 굳었다. 그런데 **막으려던 것은 블루투스의 부재가 아니라 스피커 출력이다.** 줄이어폰을 꽂은 사용자는 소리가 새지 않는데도 진동만 받았다. 이 앱을 쓰는 이유가 바로 그 상황이라 기능이 반쯤 죽어 있었다.

판정 기준을 연결 방식이 아니라 **"소리가 본인 귀로만 들어가는가"** 로 바꾼다.

| 포함 | 제외 |
|---|---|
| `wiredHeadset` · `wiredHeadphones` (3.5mm) | `builtInSpeaker` · `builtInSpeakerSafe` |
| `usbAudio` (USB-C 이어폰) | `carAudio` · `airPlay` |
| `bluetoothA2dp` · `bluetoothSco` · `bluetoothLe` | `hdmi` · `hdmiArc` · `dock` |
| `hearingAid` | `lineAnalog` · `lineDigital` · `auxLine` |

**허용 목록이다.** 모르는 장치는 자동으로 제외된다 — 안 들리는 쪽으로 틀리는 것이 새는 쪽으로 틀리는 것보다 낫다. 이름도 `isHeadphoneConnected` · `AudioRoute.headphones` 로 바꿨다. 이름에 "블루투스"가 남아 있으면 다음 사람이 같은 실수를 반복한다.

**알고 감수하는 것** — `usbAudio` 는 USB DAC 를 외부 스피커에 물린 경우도 포함한다. 그런 사용자는 극소수이고 장소별 `soundEnabled` 로 끌 수 있다. 반대로 USB-C 이어폰을 배제하면 3.5mm 잭이 없는 최신 기기에서 유선이 통째로 막힌다. `auxLine` 을 제외한 것도 같은 저울질의 반대편이다 — AUX 는 외부 스피커 연결이 주 용도다.

**재검토 조건** — 실기기에서 USB-C 이어폰이 `usbAudio` 가 아닌 다른 값으로 잡히거나, 차량 블루투스가 `bluetoothA2dp` 로 잡혀 차 스피커로 소리가 나가면.

## 019. 백그라운드 알림은 상시 포그라운드 서비스가 담당한다

**버린 것** — "백그라운드 isolate 가 알림 하나 띄우고 죽으면 된다" (#63 의 구조)

**무엇이 문제였나**

지오펜스 콜백은 전용 isolate 에서 실행된 뒤 즉시 회수된다. 그 안에서 할 수 있는 것은 판정·저장·알림 발행 한 번이 전부라, 실기기에서 네 가지가 동시에 무너졌다 (#74):

| 증상 | 구조적 원인 |
|---|---|
| 이어폰인데 무음 | 이어폰 판정·재생은 포그라운드 `AlertController` 에만 있다. 백그라운드 경로에 소리 코드가 아예 없었다 |
| 알림 1회 | `show()` 한 번 부르고 isolate 가 죽는다 |
| 진동 6초 | 채널 진동 패턴이 1회 재생되고 끝 |
| 화면이 안 덮인다 | 006 의 전제 오류 — 위 갱신 참조 |

**정한 것**

감시 대상이 있는 동안 **위치 타입 포그라운드 서비스**(`AlertWatchService`)를 유지한다. 이 서비스가:

1. 프로세스를 살려둬 Doze 중에도 콜백이 제때 온다
2. 백그라운드 isolate 가 저장한 `PendingAlert` 를 SharedPreferences 변경으로 감지해 **반복 진동**을 건다
3. `SYSTEM_ALERT_WINDOW` 로 앱을 전면에 띄운다 → 기존 `AlertController` 가 반복 진동·이어폰 확인·소리·해제까지 이어받는다

**소리는 네이티브에서 내지 않는다.** 이어폰 허용 목록 판정(018)은 Dart 에 있고 테스트로 지켜진다. 네이티브가 소리를 내면 그 판정을 우회해 스피커로 샐 수 있다. 서비스가 하는 것은 **진동과 화면 띄우기뿐**이다.

**대가로 감수하는 것**

- 상시 알림 1개가 알림 줄에 남는다. 없앨 수 없고, 없애는 방법이 있다면 정책 위반이다. 감시 대상이 0건이면 서비스를 내려 알림도 사라진다.
- Play 심사에 `SYSTEM_ALERT_WINDOW`·배터리 최적화 예외 사용 사유가 필요하다 → [09-RELEASE](09-RELEASE.md)
- 앱이 끝내 열리지 않으면 네이티브 진동을 **10분**에서 끊는다. 서랍 속 휴대폰이 배터리를 다 쓰며 떨고 있으면 안 된다. 앱이 열려 세션을 넘겨받으면 그때부터는 Dart 가 해제까지 무제한으로 이어간다.

**깨지기 쉬운 지점** — 서비스가 알림을 감지하는 신호는 `shared_preferences` 가 쓰는 `FlutterSharedPreferences` XML 의 키 변화다. 플러그인이 저장소를 DataStore 로 옮기면 이 신호가 끊긴다. 그 경우 증상은 "진동이 다시 6초에 끝난다"이고, 알림 자체는 계속 뜬다.

> **해소됨 (2026-08-14, [024](#024-android-는-하이브리드-감시로-전환한다-017-재검토-조건-발동))** — Android 는 감시 서비스가 판정 결과를 채널로 직접 받으므로 XML 키 감시가 필요 없어졌다. 리스너를 제거했다. `PendingAlert` 저장은 화면 승격 후 `AlertController` 가 세션을 이어받는 용도로만 남는다.

**재검토 조건** — 실기기에서 상시 알림에 대한 사용자 불만이 크거나, Play 가 포그라운드 서비스 사용을 반려하면. 그때는 "이벤트 발생 시에만 서비스 시작"으로 물러난다 (지오펜스 콜백 지연을 감수).

## 020. 알림 시간대는 `shouldNotify` 에서 거른다 — OS 등록은 유지한다

**상황** — 등록한 장소에 들어가기만 하면 언제든 울린다. 회사 근처에 살거나 자주 지나는 곳을 등록하면 하루에도 몇 번씩 무의미하게 울린다. 사용자가 원하는 것은 "잠실에 도착하면"이 아니라 **"출근길에 잠실에 도착하면"** 이다 ([이슈 #81](https://github.com/Cassiiopeia/EarLocAlert/issues/81)).

**정한 것**

장소마다 활성 시간 창을 0개 이상 붙이고, **`GeofenceEvaluator.shouldNotify` 에서 시각으로 거른다.** OS 지오펜스 등록은 창 밖에도 유지한다. 이벤트는 평소대로 들어와 상태 전이와 이력이 정상 기록되고, **알림만 나가지 않는다.**

이 자리가 맞는 이유는 `shouldNotify` 가 이미 "전이는 사실이고 알림은 설정이다"를 가르는 지점이기 때문이다 ([03-DOMAIN](03-DOMAIN.md)). 스케줄은 설정 쪽이다.

**기각한 것 — 창 밖이면 OS 등록을 해제한다**

배터리는 아끼지만 **알림을 유실한다.** 등록에서 빠지면 `GeofenceRegistrationSync` 가 상태를 `unknown` 으로 되돌린다. 이건 의도된 방어 장치로, 재활성화 때 묵은 `outside` 와 `initialTrigger(ENTER)` 가 만나 가짜 알림이 터지는 것을 막는다. 그 결과 창이 열려 재등록되면 `unknown → inside` 가 되고 **규칙 3(unknown 첫 판정 무알림)에 걸려 조용히 넘어간다.** 창이 열린 뒤 첫 진입을 놓치는 것은 이 기능의 존재 이유를 없앤다.

여기에 창 경계마다 앱을 깨울 백그라운드 타이머(WorkManager / BGTaskScheduler)와 재부팅 후 복구까지 붙는다.

**기각한 것 — 알림 발화 직전(`AlertController`)에서 막는다**

**너무 늦다.** 백그라운드에서는 네이티브 `AlertWatchService` 가 진동과 화면 띄우기를 먼저 하고(019), Dart 는 앱이 전면으로 올라온 뒤에야 관여한다. 여기서 막으면 이미 울린 뒤이고 이력의 `notified` 도 사실과 어긋난다.

**대가로 감수하는 것** — 창 밖에도 OS 지오펜스가 등록돼 있다. OS 위임 방식이라 앱이 도는 것이 아니어서 실제 소모는 무시할 수준이다.

**경계 동작** — 창이 열릴 때 이미 반경 안에 있어도 알리지 않는다. **창 안에서 일어난 전이만** 알림이 된다. 도착한 지 10분 지난 시점에 갑자기 울리는 것은 쓸모가 없고, 집이 창 안에 있으면 매일 아침 알람처럼 울린다.

**재검토 조건** — 실기기에서 창 밖 지오펜스 유지가 배터리에 유의미한 영향을 준다고 측정되면. 그때는 "창이 하나도 없는 장소만 상시 등록, 창이 있으면 경계에서 등록/해제"를 검토하되 위의 유실 문제를 먼저 푼다.

## 021. 반복 규칙에는 UTC 를 쓰지 않는다 (04-CONVENTIONS 예외)

**상황** — [04-CONVENTIONS](04-CONVENTIONS.md) 는 시각을 UTC 로 저장하라고 한다. 알림 시간대(020)를 그 규칙대로 저장하면 문제가 생긴다.

**정한 것**

UTC 규칙은 **일어난 사건의 시점**(`createdAt`·`occurredAt`)에 적용된다. "평일 08:00" 은 시점이 아니라 **벽시계 규칙**이므로 이 규칙을 따르지 않는다.

`AlertSchedule` 은 시각을 **자정 기준 분(0~1439) 정수**와 요일 집합으로 담고, 판정에는 **로컬 시각**을 쓴다.

UTC 로 저장하면 사용자가 다른 시간대로 이동하거나 서머타임이 적용될 때 08:00 이 07:00 으로 밀린다. 사용자가 원한 것은 "그곳의 아침 8시"이지 "UTC 23시"가 아니다. 정수 표현은 시간대와 무관하고 판정이 정수 비교라 테스트도 명확하다.

**깨지기 쉬운 지점** — `GeofenceBackgroundProcessor` 에서 같은 시계가 갈린다. 이력은 `.toUtc()`, 스케줄 판정은 `.toLocal()` 이다. 한쪽을 따라 다른 쪽을 고치면 조용히 어긋난다 — 코드에 주석으로 이유를 남겼다.

## 022. 알림음 볼륨 — 앱 재생 볼륨 + Android 시스템 볼륨 상향, 해제 시 원복

**상황** — 알림음이 시스템 미디어 볼륨을 그대로 따랐다 (이슈 #86). 시스템 볼륨이 0 이면 이어폰을 꽂고 있어도 무음이고, 사용자가 크기를 조절할 수단이 `soundEnabled` 토글뿐이었다.

**정한 것**

전역 설정 `AlertVolumeStore`(0.0~1.0, 기본 0.8)를 두고 두 겹으로 적용한다.

1. **앱 재생 볼륨** — `AlertSoundService.play(volume:)`. 양 플랫폼 동일, 권한 불필요.
2. **시스템 볼륨 상향(Android)** — 알림 시점에 미디어 볼륨이 설정값 수준보다 낮으면 거기까지 **올린다**. 이미 크면 건드리지 않고, 해제 시 원래 값으로 되돌린다. 원복용 이전 값은 네이티브가 든다 — Dart 에 두면 프로세스 재시작에서 유실된다.

iOS 는 시스템 볼륨을 바꾸는 공개 API 가 없어 1번만 동작한다. 이 차이는 받아들인다 — 사설 API 는 심사 거부 사유다.

**순서가 규칙 5 를 지킨다.** 시스템 볼륨 상향은 **이어폰 경로가 확정된 뒤**에만 한다. 이어폰이 없으면 볼륨을 건드리지 않는다 — 재생도 없는데 볼륨만 올리면 다른 앱 소리가 갑자기 커진다. 네이티브 `system_volume` 채널은 소리를 내지 않는다(019) — 하는 것은 볼륨 숫자 조정뿐이다.

**장소별이 아니라 전역이다.** "이 장소는 크게"가 필요해진 사례가 없고, 장소마다 다르면 왜 지금 작게 울렸는지 사용자가 추적해야 한다.

**방해금지 모드는 뚫지 않는다.** `setStreamVolume` 이 SecurityException 을 던지면 삼키고 재생만 계속한다. `ACCESS_NOTIFICATION_POLICY` 를 받으면 뚫을 수 있으나, 방해금지는 사용자의 명시적 의사라 앱이 우회하면 안 된다.

**깨지기 쉬운 지점** — 원복은 `_silence()` 안에 있다. 해제 경로를 고치면서 이 호출을 빼면 알림이 끝나도 볼륨이 올라간 채 남는다.

## 023. 권한 온보딩 — 반드시 한 번은 묻고, 어느 단계에서든 나갈 수 있다

**상황** — 온보딩이 두 방향으로 어긋나 있었다 (이슈 #90).

- 신뢰성 권한(#74) 안내가 **화면에 나타나지 않고** 홈으로 넘어갔다. 화면이 "이미 안내했는가"라는 저장값을 읽기 전에 "이미 안내했다"로 추측했기 때문이다. 권한이 이미 허용된 기존 사용자는 권한 조회가 먼저 끝나므로 안내가 통째로 사라졌고, 기록도 남지 않아 **다음 실행에서도 영영 반복**됐다.
- 반대로 필수 권한이 거부(재요청 가능)된 상태에서는 **나갈 방법이 없었다.** 영구 거부일 때만 이탈을 허용했는데, iOS 는 한 번 거부하면 다이얼로그를 다시 띄우지 않으므로 버튼이 아무 일도 하지 않는 화면에 갇힌다.

**정한 것 — 두 원칙은 서로를 배반하지 않는다.**

1. **묻긴 한다.** 모든 단계는 최소 한 번 화면에 나타난다. 판정에 쓰는 값이 전부 준비되기 전에는 단계를 결정하지 않는다. **읽지 못한 값을 추측하지 않는다.**
2. **가두지 않는다.** 완료 화면을 뺀 모든 단계에 "나중에 하기"가 있다. 필수든 선택이든, 거부든 미요청이든 사용자는 홈에 닿는다.

`PermissionGate.canLeaveOnboarding` 을 **제거했다.** 언제나 나갈 수 있으므로 판정이 아니다. 항상 참인 판정을 남겨두면 호출부가 그것으로 조건문을 만들고, 그 조건문이 다시 틀린다.

**모르는 값의 기본은 "한 번 더 묻는다"로 통일한다.** 저장소(`PrefsReliabilityPromptStore.wasSeen`)는 읽기 실패를 "안내 안 함"으로 보는데 화면만 반대였다. 한 번 덜 묻는 쪽을 택한 결과가 영구 미노출이었다.

**A-12 를 코드가 따라온 것이다.** [01-REQUIREMENTS](01-REQUIREMENTS.md) 와 [06-UX](06-UX.md) 는 처음부터 "권한을 거부해도 앱은 정상적으로 열린다"고 적고 있었다. 어긋난 쪽은 코드였고, 테스트가 그 코드를 고정하고 있었다. **권한 없이도 기본 화면에 닿아야 한다는 App Store 심사 방침과도 이 방향이 맞다.**

**006 을 뒤집지 않는다.** 신뢰성 권한은 여전히 선택이고, 없어도 앱은 성립해야 한다. 바꾼 것은 *강제 여부*가 아니라 *안내 여부*다. 실기기에서 배터리 최적화 예외 없이 알림이 지연되는 것은 사실이지만, 그 답은 강제가 아니라 잘 묻는 것이다 — 강제는 심사에서 막힌다.

**깨지기 쉬운 지점** — "안내했다"는 기록(`markSeen`)은 사용자가 그 화면에서 버튼을 누른 경로에만 있다. 화면을 건너뛰는 경로를 새로 만들면서 기록을 함께 남기면 #90 이 그대로 재현된다. 반대로 안내하고도 기록하지 않으면 켤 때마다 같은 화면이 뜬다.

**필수 권한을 건너뛴 사용자는 앱을 켤 때마다 온보딩을 본다.** 기록을 남기지 않기 때문이다. 이건 의도다 — 그 권한 없이는 앱이 아무것도 하지 못하고, "나중에 하기"가 항상 있어 한 번 누르면 지나간다.

## 024. Android 는 하이브리드 감시로 전환한다 (017 재검토 조건 발동)

**버린 것** — Android 에서의 `native_geofence` 이벤트 경로

**무엇이 문제였나** ([이슈 #93](https://github.com/Cassiiopeia/EarLocAlert/issues/93))

앱을 켜지 않으면 도착 알림이 발화되지 않았다. 도착 후 앱을 실행하는 순간에야 울렸다. 실기기에서 확인한 것:

| 확인 항목 | 결과 |
|---|---|
| `AlertWatchService` 생존 | **살아있음** (상시 알림 표시 중) |
| 배터리 최적화 예외 | **허용됨** |
| 도착 시점 알림 | **없음** (알림도 진동도) |
| 앱 실행 직후 | **즉시 발화** |

서비스도 살아있고 Doze 예외도 받은 상태에서 발화가 없었다. **발화 주체의 문제가 아니라 이벤트가 도달하지 않았다.**

`native_geofence` 1.2.1 은 지오펜스 브로드캐스트를 받은 자리에서 처리하지 않고 WorkManager 에 넘긴다. 거기에 두 결함이 있다.

- `setExpedited(RUN_AS_NON_EXPEDITED_WORK_REQUEST)` — 즉시 실행 쿼터가 소진되면 일반 작업으로 강등되어 Doze 와 앱 대기 버킷 제한을 그대로 받는다. 쿼터는 앱 사용 빈도로 결정되므로 **앱을 쓰지 않을수록 알림이 오지 않는다.** 이 앱의 사용 패턴과 정확히 반대다
- `ExistingWorkPolicy.APPEND` — 선행 작업이 FAILED/CANCELLED 면 뒤에 붙는 작업도 같은 상태가 되어 실행되지 않는다. 그리고 해당 워커에는 `Result.failure()` 반환 지점이 셋 있다(콜백 핸들 없음·콜백 정보 조회 실패·엔진 null)

**구조적 결함은 실패 가능한 엔진 부팅을 이벤트마다 반복한다는 점이다.**

앱을 켜면 울린 이유는 부트스트랩이 지오펜스를 전부 재등록하고 `initialTriggers: {enter}` 가 즉시 발화하기 때문이다. 도착해서 울린 것이 아니라 **재등록되며 울린 것**이고, 실제 도착 이벤트는 유실됐다.

플러그인 경로는 고칠 수 없다 — PendingIntent 목적지가 그 패키지 리시버로 하드코딩되어 있어 가로챌 수단이 없다.

**정한 것**

Android 는 앱이 `GeofencingClient` 에 직접 등록하고, 앱 소유 리시버가 이벤트를 받아 `AlertWatchService` 로 직행한다. WorkManager 를 경로에서 걷어낸다.

1. **감시 서비스가 Flutter 엔진을 상시 보유한다.** 실패 지점이 이벤트마다 재실행되던 것이 원인이므로, 한 번 띄워 들고 있는 것이 근본 수정이다
2. **장소마다 지오펜스를 둘 등록한다** — 근접 반경(`max(반경 × 3, 500m)`)과 실제 반경. 근접은 정밀 감시를 켜는 트리거, 실제는 정밀 감시가 실패했을 때의 폴백이다. 하나만 두면 한쪽이 죽을 때 발화가 통째로 사라진다
3. **근접 반경 안에서만 위치 스트림을 돈다** (5초/10m, 30분 상한). 평소에는 OS 지오펜스라 소모가 없다
4. 재부팅 복구 리시버를 추가한다 — 권한과 주석은 있었으나 정작 리시버가 없었다

판정은 Dart 에 그대로 둔다. 두 경로(정밀 측정·OS 전이)가 **같은 판정 함수와 같은 상태 저장소로 수렴**하므로 중복 발화가 구조적으로 불가능하다.

**017 이 정밀 감시를 버린 근거는 이미 무효였다** — "FGS 는 제조사 절전에 죽는다"였는데, 019 에서 상시 FGS 를 도입했고 실기기에서 살아있음이 확인됐다. 죽을까 봐 피했던 것이 이미 돌고 있었다.

**iOS 는 바꾸지 않는다.** WorkManager 가 없고 CLLocationManager region monitoring 을 직접 쓰므로 이 결함이 존재하지 않는다. `GeofenceMonitor` 인터페이스가 플랫폼을 가려 Android 구현만 교체했다.

**대가로 감수하는 것**

- Android 전용 네이티브 코드가 늘고, **자동 테스트가 닿지 않는 영역이 생긴다.** 이 프로젝트에 Android 단위 테스트 인프라가 없어 Kotlin 계층은 빌드 통과와 실기기 검증으로만 닫힌다. Dart 계층(판정 조율·근접 반경·채널 어댑터)은 전부 테스트한다
- 정밀 모드가 도는 동안 배터리 소모가 는다. 근접 반경 안에서만·30분 상한으로 제한했으나 **실측 전이다**
- 파라미터(근접 반경 3배/최소 500m, 갱신 5초/10m, 상한 30분)가 전부 추정치다

**재검토 조건** — 실측에서 배터리 영향이 크면 근접 반경과 갱신 주기를 줄인다. `native_geofence` 가 WorkManager 경유를 버리면 되돌리는 것을 검토한다. 정밀 모드 전환 지연이 셔틀버스 시나리오에 여전히 부족하면 근접 반경을 넓힌다.

## 025. 백그라운드 알림 발화 주체는 네이티브다 — 알림도 거기서 만든다

**언제** — 2026-08-19 (이슈 #102)

**무엇이 문제였나**

024 로 Android 감시 경로를 하이브리드로 바꾸면서 **어떤 OS 알림도 발행되지 않는 상태가 됐다.**

`GeofenceBackgroundProcessor` 는 진입점마다 알림 발행 여부가 다르다. `handle`(iOS)만 `alertPort.notify()` 를 부르고, Android 가 쓰는 `handleTransition`·`handlePosition` 은 "발화 주체가 네이티브"라는 전제로 알림을 넘겼다. 그런데 `AlertWatchService.beginAlert()` 는 진동과 액티비티 시작만 하고 알림을 만들지 않았다.

**전제가 코드로 옮겨지지 않았고, 아무도 그 자리를 채우지 않았다.**

결과: 오버레이 권한이 없거나 백그라운드 액티비티 시작이 막히면 **진동만 울리고 화면에 아무 흔적도 남지 않는다.** 앱을 직접 열어야 저장된 `PendingAlert` 가 살아나 그제서야 울렸다. #74 가 만든 `BackgroundAlertNotifier`(전체화면 인텐트·알람 카테고리·스와이프 방지)는 코드에 남아 있었으나 Android 경로에서 호출되지 않았다.

**정한 것**

**네이티브가 알림을 만든다.** Dart 로 되돌리지 않는다.

- 발화 순서는 **알림 → 진동 → 화면 승격**이다. 뒤로 갈수록 실패 가능성이 높은 것을 뒤에 둔다
- 채널을 `ear_loc_alert_geofence`(Dart)와 나눈다. 그 채널은 진동이 켜져 있고 — 앱 프로세스가 없는 iOS·구 경로에서는 그것 말고 진동 수단이 없다 — 여기서는 서비스가 직접 반복 진동을 걸어 겹치면 패턴이 어긋난다. **채널 설정은 최초 생성 시 고정되어 나중에 못 바꾸므로 공유할 수 없다**
- 알림 id 는 `BackgroundAlertNotifier.notificationId`(2001)와 **같은 값을 쓴다.** 앱이 승격·정리할 때 그 id 로 취소하기 때문이다
- 전체화면 인텐트를 건다. 화면이 꺼졌거나 잠긴 상태를 이것이 담당하고, 켜져 있을 때는 오버레이 권한이 담당한다
- **소리는 여전히 내지 않는다.** 채널을 `setSound(null, null)` 로 만든다 — 이어폰 판정은 Dart 에만 있고 (019), 네이티브가 소리를 내는 순간 그 판정이 우회된다

**왜 Dart 가 아닌가** — 판정 엔진이 죽어도 알림은 떠야 한다. 그리고 진동을 거는 주체와 알림을 만드는 주체가 다르면 "울리는데 끌 방법이 없는" 상태(#83, #84)가 다시 생긴다.

**함께 고친 것**

- **화면 승격 실패를 기록한다.** 권한 없음과 백그라운드 액티비티 시작 차단을 구분해 남긴다. 예전에는 둘 다 조용히 return 이라 진단 기록으로 추적할 수 없었다
- **설정 화면에 알림 도달 권한을 둔다.** 신뢰성 권한(#74)은 온보딩의 선택 단계라 한 번 지나가면 다시 묻지 않는데, 나중에 켤 자리가 앱 어디에도 없었다. 홈 배너가 유일한 경로였고 그것을 놓친 사용자는 "권한을 다 줬는데 왜 안 되는가"에 갇혔다
- **시간 초과 시 알림을 지울 수 있게 바꿔 단다.** `ongoing` 인 채로 두면 진동은 멎었는데 지울 수 없는 알림이 영영 남는다

**대가로 감수하는 것**

- 알림 채널이 하나 더 늘어 Android 설정에 "위치 감시"·"도착·출발 알림" 둘이 보인다
- **Kotlin 계층이라 자동 테스트가 닿지 않는다** (024 와 같은 한계). 채널 계약(`AlertDecision`)만 Dart 쪽에서 테스트된다

## 026. 진동 세기는 진폭과 길이를 함께 바꾼다

**언제** — 2026-08-19 (이슈 #103)

**무엇이 문제였나**

이 앱은 이어폰이 연결됐을 때만 소리를 낸다 (019). 즉 **대부분의 알림은 진동이 전부인데**, 그 세기를 사용자가 정할 수 없었다. 알림음 크기(022)만 설정에 있었다.

**정한 것**

세기 단계를 셋(약함·보통·강함)으로 두고, 각 단계가 **진폭과 길이를 함께** 바꾼다.

`VibrationEffect` 의 진폭 제어(`hasAmplitudeControl`)를 지원하지 않는 기기가 아직 많다. 진폭만 바꾸면 그런 기기에서 설정이 아무 효과도 없고, 사용자는 설정이 고장 났다고 판단한다. 길이는 어느 기기에서나 통하므로 **폴백이 아니라 함께 가는 축**으로 둔다.

기본값은 지금까지의 동작과 같은 세기다 — 설정을 새로 만들었다고 기존 사용자의 알림이 달라지면 안 된다.

**설정을 읽는 자리는 Dart 한 곳이다.** 네이티브가 SharedPreferences 를 직접 읽게 하면 읽는 자리가 둘이 되어 반드시 어긋난다. 판정 결과(`AlertDecision`)에 실어 보내고, 네이티브는 받은 값을 쓰기만 한다. 값이 0 이면 "설정 없음"으로 기존 기본 진동에 떨어진다.

알림음 크기와 같은 **전역 설정**이다 — 장소별로 두지 않는다 (022 와 같은 이유).

**대가로 감수하는 것**

- 채널 계약(`AlertDecision`)에 필드가 둘 늘었다. 한쪽만 바꾸면 진동이 조용히 기본값이 된다 — 계약 테스트가 이것을 지킨다
- 단계별 진폭·길이 수치가 추정치다. 실기기에서 체감 차이가 없으면 조정한다

## 027. 인앱 업데이트는 설치 화면까지만 한다

**언제** — 2026-08-19 (이슈 #104)

**무엇이 문제였나**

스토어 배포 전까지 사이드로드가 유일한 배포 경로다. 새 버전이 나와도 앱 안에서 알 방법이 없어, 릴리스 페이지를 열어 APK 링크를 찾아 내려받고 설치하는 왕복이 검증마다 반복됐다.

**정한 것**

설정 화면에서 GitHub 공개 릴리스 API 로 최신 버전을 확인하고, APK 를 내려받아 **설치 화면을 띄우는 것까지** 한다.

- **설치를 대신 하지 않는다.** 실제 설치는 사용자가 그 화면에서 확인한다. 대신 눌러줄 API 도 없고, 있어도 그렇게 하면 안 된다
- **토큰을 쓰지 않는다.** 공개 레포의 공개 릴리스만 읽는다. 인증을 붙이면 앱에 자격 증명을 넣어야 하고 APK 를 뜯으면 나온다
- **확인은 사용자가 누를 때만 나간다.** 설정 화면을 열 때마다 조회하면 요청 한도만 소모한다
- **실패를 "최신"으로 뭉뚱그리지 않는다.** 확인했다고 믿는데 실제로는 확인이 안 된 상태가 가장 나쁘다. 네트워크 단절·응답 이상·버전 파싱 실패를 사유와 함께 알린다
- **버전 비교는 숫자로 한다.** 문자열 비교면 `1.10.0 < 1.9.0` 이 되어 새 버전이 영영 보이지 않는다
- APK 는 앱 캐시에 쓴다 — 외부 저장소 권한이 필요 없고 OS 가 정리한다. FileProvider 공유 범위는 그 하위 하나로 제한한다

**Android 전용이다.** iOS 는 사이드로드 경로가 없다.

**대가로 감수하는 것**

- `REQUEST_INSTALL_PACKAGES` 권한이 는다. **Play 심사에서 설명이 필요한 항목이고**, 스토어 배포가 시작되면 이 권한·채널·화면을 함께 걷어낸다 → [11-ROADMAP](11-ROADMAP.md)
- 앱이 네트워크로 나가는 대상이 하나 늘었다 (광고 외에 GitHub API·릴리스 자산). 위치나 사용자 정보는 여전히 나가지 않는다

## 028. 진단 기록은 파일에서 직접 읽고, 깨진 바이트를 견딘다

**언제** — 2026-08-20 (이슈 #106)

**무엇이 문제였나**

**진단 화면이 항상 "0건"이었다.** 파일에는 1400줄 넘게 쌓여 있는데도.

원인이 둘 겹쳐 있었다.

**(1) 화면이 전역 로거를 거쳐 읽었다.**

```dart
final content = await Diagnostics.logger.readAll();
```

`Diagnostics.logger` 는 앱 시작 시 `init()` 이 성공해야 파일 로거가 된다. 실패하면 아무것도 하지 않는 로거로 남고 그 `readAll()` 은 무조건 빈 문자열이다. **진단 화면이 진단 대상의 초기화 성공에 의존하고 있었다** — 정확히 그것이 실패했을 때 열리는 화면인데.

특히 Kotlin 계층은 Dart 초기화와 무관하게 파일에 직접 쓴다. 그래서 `[watch]`·`[registrar]` 기록이 통째로 안 보였다.

**(2) 파일이 UTF-8 로 깨져 있었고, 읽기 실패가 "기록 없음"으로 둔갑했다.**

```
FileSystemException: Failed to decode data using encoding 'utf-8'
```

```dart
try {
  return await file.readAsString();
} on Object {
  return '';        // ← 읽기 실패가 "로그 없음"이 된다
}
```

**이 파일은 세 곳이 함께 append 한다** — 앱 isolate, 감시 서비스 엔진(별도 isolate), Kotlin 계층. 쓰기가 겹치면 한글 한 글자(UTF-8 3바이트)가 중간에서 잘린다. `readAsString()` 은 그 순간 통째로 예외를 던지고, 그것을 삼키면 **한 글자 때문에 수천 줄이 사라진다.**

**정한 것**

1. **화면은 파일을 직접 읽는다** (`DiagnosticLogReader`). 전역 로거 초기화 성공 여부와 무관하다
2. **깨진 바이트를 견딘다** — `allowMalformed: true` 로 디코딩한다. 깨진 자리는 대체 문자가 되고 그 줄만 이상해 보일 뿐, 나머지는 전부 읽힌다. Kotlin 회전도 같게 바꿨다 — 거기서 예외가 나면 회전이 영영 실패해 파일이 상한을 넘은 채 자란다
3. **"기록 없음"과 "읽지 못함"을 구분해 보여준다.** 못 읽는 중에 "기록이 없습니다"를 보면 사용자는 감시가 안 도는 줄 알고 없는 문제를 찾게 된다
4. **화면을 열었다는 사실 자체를 기록한다.** 다음에 열었을 때 그 줄이 보이면 로깅이 살아있다는 증거다 — 사용자가 스스로 가릴 수 있는 가장 단순한 신호다

**동시 쓰기 자체는 그대로 둔다.** 프로세스 간 락은 Dart·Kotlin 양쪽에 걸어야 하고, 로깅이 판정 경로를 붙잡는 위험이 깨진 줄 하나보다 크다. **읽는 쪽이 견디는 것이 옳은 지점이다.**

**함께 고친 것**

- **로그를 알림 경로 전반에 남긴다** — 세션 시작·오디오 판정(이어폰 연결 여부와 장소 설정, 그 결과)·재생 실패·해제·대기열, 권한 여섯 값, 장소 추가/수정/삭제/토글, 앱 생명주기. "왜 소리가 안 났나"가 이제 한 줄로 답이 나온다
- **권한 상태는 바뀌었을 때만 남긴다.** 컨트롤러가 화면 구독마다 재생성되어 같은 줄이 초 단위로 여섯 번씩 쌓였고, 그러면 정작 찾아야 할 발화 기록이 그 사이에 묻힌다

**왜 이것이 안 잡혔나**

로거 단위 테스트는 있었으나 **화면이 실제로 무엇을 읽는지 확인하는 테스트가 없었다.** 깨진 바이트 시나리오도 없었다. 둘 다 회귀 테스트로 덮었다 (`diagnostic_log_reader_test.dart`).
