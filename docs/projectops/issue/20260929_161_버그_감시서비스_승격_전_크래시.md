🗒️ 설명
---

**프로세스가 처음부터 새로 떠서 감시 서비스를 시작할 때(콜드 스타트), 시작이 조금 늦어지면 서비스가 포그라운드로 올라가기 전에 OS 에 의해 크래시한다.** 크래시는 프로세스째 일어나고, 앱의 진단 기록에는 그 직전 줄까지만 남는다. 사용자가 보기에는 "감시가 조용히 꺼진" 것과 같다.

#159(3일간 도착 신호가 끊긴 문제)를 검증하려고 에뮬레이터에서 앱 교체, 강제 종료, 프로세스 킬을 밟다가 발견했다. **#159 의 원인이라고 확정하지는 못한다.** 다만 "프로세스가 죽었는데 흔적이 없다"는 그 증상과 맞는 후보이고, 지금까지 기록으로는 가릴 수 없던 종류의 결함이다.

### 밟은 것과 결과 (에뮬레이터 API 36, 릴리스 아닌 debug 빌드)

**앱 교체 직후 감시 서비스 콜드 스타트 — 크래시 재현**

```
08:12:03 [boot] 복구 시작 사유=앱교체
08:12:03 [watchdog] 지오펜스 복구 요청 사유=앱교체 1곳        ← 사본으로 등록 복구는 성공
08:12:04 [watch] 감시 서비스 생성
                         ↓ 34초 동안 아무 기록 없음
08:12:38 [watch] 서비스 시작 요청 사유=앱교체
08:12:38 [engine] 감시 엔진 시작
08:12:38 [watch] 감시 서비스 종료                              ← 0.3초 뒤 종료
```

시스템 로그:

```
W/ActivityManager: Bringing down service while still waiting for start foreground: ... AlertWatchService
E/AndroidRuntime: ForegroundServiceDidNotStartInTimeException:
    Context.startForegroundService() did not then call Service.startForeground()
I/ActivityManager: Process kr.suhsaechan.ear_loc_alert has died
```

다음에 앱을 켰을 때 새로 넣은 종료 사유 기록이 이 크래시를 잡아냈다.

```
08:15:38 [exit] 프로세스 종료 이력 사유=크래시 시각=08:12:39 중요도=400 설명=crash
```

**같은 경로의 다른 측정값**

| 상황 | 서비스 생성 → 시작 요청 |
|---|---|
| 앱 교체 직후(부하 큼, 에뮬레이터 두 대 부팅 중) | **34초 → 크래시** |
| 앱 교체 직후(첫 검증 때, 부하 보통) | 7.2초 |
| 강제 종료 후 앱 실행(부하 작음) | 2.3초 |

**그 외 확인된 것 (정상)**
- `kill -9` 후 약 4초 만에 시스템이 서비스를 되살리고(`사유=시스템재시작`), 엔진이 지오펜스 복원을 요청하고 등록에 성공한다.
- 앱 교체 후 사본으로 지오펜스 복구 요청이 나간다.
- 순간이동한 위치(30km)는 위치 튐 방어가 무시한다(`사유=위치튐 955km/h`).

### 원인 추정

감시 서비스는 만들어질 때(생성 단계) Flutter 엔진을 **동기적으로** 띄우고, 포그라운드 승격은 그 다음 단계(시작 명령 처리)에서 한다. `startForegroundService()` 로 시작하면 OS 는 정해진 시간 안에 승격하기를 요구하는데(약 10초), 엔진 부팅이 그 시간을 넘기면 위 예외로 프로세스가 죽는다. 엔진 부팅은 프로세스가 콜드일 때, 기기 부하가 클 때, 저사양 기기일 때 느려진다. 릴리스(AOT) 빌드가 debug 보다 빠르므로 실기기에서의 빈도는 다를 수 있으나, **7.2초가 이미 한도의 대부분**이라 여유가 넉넉하지 않다.

이 서비스를 콜드로 여는 경로는 지오펜스 브로드캐스트 수신, 재부팅, 앱 교체(#159 에서 추가), 6시간 주기 점검 모두다.

🔄 재현 방법
---

1. debug 빌드를 에뮬레이터에 설치하고 장소를 등록해 감시를 켠다.
2. 기기 부하를 높인 상태(에뮬레이터 여러 대 부팅 등)에서 `adb install -r` 로 앱을 교체한다. 앱은 열지 않는다.
3. 진단 기록에서 `감시 서비스 생성` 다음 줄이 수 초 뒤에 나오는지, 시스템 로그에 `ForegroundServiceDidNotStartInTimeException` 이 있는지 본다.
4. 다음 실행 때 `[exit] 사유=크래시` 가 남는지 본다.

**재현은 부하에 좌우된다.** 부하가 작을 때는 재현되지 않았다(2.3초).

### 함께 발견한 낮은 심각도 항목

- **진단 기록의 `사유=재부팅` 이 재부팅이 아닐 때도 찍힌다.** 이 에뮬레이터(Android 16)에서는 앱을 강제 종료했다가 다시 실행할 때마다 부팅 완료 브로드캐스트가 다시 전달되어 `[boot] 복구 시작 사유=재부팅` 이 찍혔다(가동 8분인 기기). 동작에는 문제가 없고 복구도 되지만, 나중에 로그로 "재부팅했다"고 오해할 수 있다. 실기기에서도 그런지는 미확인.
- **도착 알림 발화의 끝에서 끝까지는 이 환경에서 확인하지 못했다.** 앱이 백그라운드일 때 에뮬레이터가 위치 소비자가 없어 주입한 위치를 전달하지 않는다. 실기기 확인이 필요하다.
